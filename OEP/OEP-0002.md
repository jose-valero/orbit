# OEP-0002 — Feasibility Probe: Does the Playbook Mechanism Generalise?

**Status:** Draft — run in progress
**Type:** Experimental
**Version:** 0.1.0
**Date:** 2026-09-30
**Depends on:** OEP-0001

---

## 1. Purpose

OEP-0001 validated a narrow mechanism — a small maintained playbook, derived
per-ticket, with write-back — for **one recurring task class** (migrating a
React view from legacy to current patterns) in **one codebase**
(`solari_cloud`). Its own §11.7 left the generalisation question open.

OEP-0002 tests generalisation along the two axes that matter most for the
new working hypothesis for ORBIT (a base for starting and running frontend
projects with AI, not just migrating them):

- **Axis 1 — different task type, same codebase.** Does the mechanism help
  on heterogeneous feature tickets that are *not* the same repeated
  procedure, only related by shared project conventions?
- **Axis 2 — no legacy pattern to distill from.** Does the mechanism help on
  genuinely new feature work, where the playbook cannot be built from
  before/after diffs (there is no "before"), only from architecture docs and
  one control ticket?

If H2 (axis 2) fails, that is a direct, load-bearing finding against
"ORBIT as a base for starting new projects" — the part of the current
hypothesis with zero evidence behind it. A failure here is not a setback to
paper over; it is exactly the answer this probe exists to get.

---

## 2. Hypotheses

**H1 (Solari, axis 1)** — A general project playbook (conventions + gotchas
of `solari_cloud` frontend work, not specific to any one task type) plus a
per-ticket derived context, produces measurable savings (time, rework,
avoidable misunderstandings) across **heterogeneous** feature tickets in an
existing codebase, relative to the operator's normal ad-hoc process.

**H2 (AssetMind, axis 2)** — The same mechanism produces measurable savings
when the playbook cannot be distilled from real before/after diffs, only
from architecture docs, decision records, and one control-ticket transcript.

Kill criterion for H2: if the ORBIT-arm ticket in AssetMind shows context
size, review time, or rework equal to or worse than the control ticket, the
mechanism does not obviously extend past migration/maintenance work, and
"starter for new projects" needs to be rethought before any product design.

---

## 3. Scope

**Lab A — `solari_cloud`, shadow run, analysis only.**
No commit, no branch, no push. All edits happen in the working tree of an
already-clean `master`, are diffed for the record, then discarded
(`git checkout --`). No experiment artifact (playbook, derived context,
metrics) is ever written inside the `solari_cloud` repo — all of it lives in
`orbit/OEP/`. This is a company repo; nothing about this probe should be
visible in its history.

**Lab B — AssetMind, real.** Normal commits, it is the operator's own repo.

**Explicitly out of scope (deferred to a future OEP if H1/H2 hold):**
core+feature-module playbook structure, independent verification, tooling/
CLI, general principles, any starter/product design.

## 4. Task Assignment

### Lab A — solari_cloud

Three real tickets, heterogeneous by design (this is the point — they are
not the same procedure, only the same codebase and conventions):

| # | Ticket | Arm | Shape |
|---|---|---|---|
| 1 | [FE] Eliminar obligatoriedad de "responder a" en notificaciones mail | **Control** | Trivial — single function, no UI structural change |
| 2 | [FE] Mostrar IBAN/Alias de cobro en ficha del cliente (solo un mercado) | **ORBIT** | Moderate — new read-only fields sourced from an existing endpoint, into an existing detail view |
| 3 | [FE-0250][FE] Estado de Razón social + excluir inactivas de selectores | **ORBIT** | Larger — table column/badge + two selector call sites + possible backend field gap |

Ticket 1 runs first as control specifically because it is small: fast to
execute, low variance, and its transcript plus a read of
`docs/architecture/frontend/` seeds the playbook without costing much time.
Tickets 2 and 3 escalate in size, mirroring the Barrios→Zonas→Employees
progression in OEP-0001, but this time the escalation is across genuinely
different feature shapes, not repetitions of one procedure.

### Lab B — AssetMind

| # | Ticket | Arm | Shape |
|---|---|---|---|
| 1 | "Inspecciones" — global list view of all inspections across assets | **Control** | Moderate — no such page exists yet, but schemas/hooks/types for `Inspection` already exist (`features/inspections/`) |
| 2 | "Recomendaciones" — global list view of open recommendations across assets | **ORBIT** | Moderate — no existing feature folder, no existing aggregate endpoint/type across assets (only a per-asset `open_recommendations` shape inside `TechnicalSummary`, `api/types.ts:142`) |

missing. "Recomendaciones" has no existing feature folder or cross-asset

ORBIT arm: it is the harder, more novel case, and the one that actually
tests H2.

## 5. Playbook Bootstrap Rules (both labs)

Same discipline as OEP-0001: ≤300 lines, every line expensive to
reconstruct, distillation not a pointer to docs.

- **Lab A source material:** ticket-1 transcript + relevant
  `docs/architecture/frontend/` files (decision-guide, forms, modals,
  policies, searchers-and-filters, DataTable) + policy/permission conventions
  touched during ticket 1. No before/after diffs this time — the tickets are
  not migrations.
- **Lab B source material:** ticket-1 transcript + `docs/FRONTEND_ARCHITECTURE.md`
  + `docs/UI_UX_GUIDELINES.md` + `docs/DECISIONS.md` + the existing
  `features/assets/` and `features/inspections/` folders as structural
  reference (how a list feature is shaped in this repo). No before/after
  diffs — nothing here has a legacy version.

---

## 6. Metrics

Same definitions as OEP-0001 §7, with one adaptation: in this session the
operator supplied full ticket text for all five tickets up front rather than
writing each brief live. To keep the control/ORBIT comparison honest, on the
ORBIT-arm tickets the derivation step uses **only** the ticket's own text
(treated as the delta brief) plus the playbook plus directly relevant source
files — not a fresh, unbounded re-read of the codebase. Context size,
correction lines, review time, rework, and prior-gotchas-applied are
recorded exactly as in OEP-0001.

## 7. Results — running log

### 7.1 Lab A — Ticket 1 (Control): notification mail "responder a"

- Size: trivial (single-file change).
- Investigation: grepped for the field across `pages/MailNotification/`,
  read `MailNotificationForm.jsx` and `helperMailNotification.js`.
- Root cause found: `isRequiredMail(notificationSelected)` returns `true`
  for every category except `issued_invoice` and `new_payment`. All other
  wiring (abbr `*`, hint copy, conditional validation
  `validations().email.validate` vs `validations().email_format.validate`)
  already branches on this correctly — only the source of truth needed to
  change.
- Fix: collapsed `isRequiredMail` to `() => false`. 1 file, −13/+1 lines.
  Verified no other call sites assume category-based behavior (`grep`
  confirmed 2 call sites, both just consume the boolean).
- Diff captured, then reverted (`git checkout --`); `solari_cloud` working
  tree left clean.
- Avoidable misunderstandings: 0. Rework: 0. Regressions: n/a (shadow run,
  not deployed).
- Notes for playbook bootstrap: the codebase's pattern for "conditionally
  required field" is a small pure function consumed both for the `abbr`
  marker and the validation branch — worth a playbook line, since a naive
  fix could have hardcoded `false` in the JSX instead of at the source of
  truth, leaving the stale per-category logic as dead, misleading code.

### 7.2 Playbook bootstrap

Built from `docs/architecture/frontend/{decision-guide,policies,DataTable,
searchers-and-filters}.md` + the ticket-1 transcript. No before/after diffs
(these tickets are not migrations). Result:
`orbit/OEP/drafts/SOLARI-FRONTEND-PLAYBOOK.md`, ~85 lines. Distilled to
defaults + gotchas, not a copy of the four source docs (which run to
~1,400 lines combined).

### 7.3 Lab A — Ticket 2 (ORBIT): IBAN/Alias in client detail

- Derivation: playbook (policies/DataTable conventions — not directly
  applicable here, this ticket doesn't touch a table-as-listing or policies)
  + the 3 files the ticket named + one file found by grep
  (`client_payment_methods_controller.rb` was a red herring; the real
  endpoint is `clients_controller.rb#client_payment_methods`).
- **Key finding, backend already correct:** `clients_controller.rb:100`
  already does `render json: cpgs.as_json(methods: %i[client_account_alias
  client_account_number])` — the fields the ticket says are missing from the
  frontend are **already present on every `cpg` record** the table
  receives. Confirmed by reading the controller directly rather than
  trusting the ticket's "Estado actual" section at face value. Zero backend
  work needed, despite the ticket's ambiguity between "Opción A" and
  "Opción B."
- Implementation: **Opción B** (table column, not the detail tab), because
  a pre-existing pattern in the same file already does almost exactly this
  — `PGTable.jsx` shows `current_number_in_gateway` for AutoDebitNet rows, gated
  `isAdminSupport() && gateway_name === 'AutoDebitNet'`. Copied the shape but
  dropped the `isAdminSupport()` gate, because the ticket's whole point is
  that non-admin billing staff need to see this without opening the
  gateway form — gating it to admin-only would have silently defeated the
  ticket while looking like a correct implementation.
- Scope: 2 files (`Header.jsx`, `PGTable.jsx`), +40/-0 lines. Gated on
  `gateway_name === 'AutoDebitNet'` alone (not a separate country flag) — IBAN/Alias
  only exist for the AutoDebitNet gateway, which is specific to one market by construction,
  so a redundant country check would be dead code.
- Avoidable misunderstandings: 0. Rework: 0. Verified by reading the
  controller's `as_json` call directly rather than assuming from the
  ticket text — this is the check that mattered.
- Diff captured, then reverted; `solari_cloud` working tree left clean.

### 7.4 Lab A — Ticket 3 (ORBIT): Razón social status + exclude inactive from selectors

- Derivation: the 3 files the ticket named + `app/models/invoicing/
  billing_entity.rb` + a migration grep.
- **Key finding, the ticket's own "Estado actual" is confirmed correct and
  the ticket is bigger than its file list implies:** `BillingEntity` has no
  `active`/`status`/`enabled` column at all — grepped the model and
  migrations, nothing. This is genuinely a full-stack ticket: a DB column +
  migration + exposing it on the relevant endpoints is a prerequisite that
  no frontend change can substitute for.
- **Second finding — the ticket's own file list is partly wrong.** Of the
  three referenced files, only `Table.jsx` needs a frontend change (a
  badge). The two selector files
  (`Clients/context/formContext.js`, `useBillingEntitiesCollection.js`) call
  a shared backend endpoint (`/invoicing/billing_entities/search_collection`)
  — excluding inactive firms belongs in that endpoint's Ransack scope, not
  in either frontend file. Editing the frontend files to filter client-side
  would have been wrong: it would silently break pagination/counts on that
  endpoint. Recorded as a playbook rule: **"selector exclusion" tickets are
  usually a backend scope change, not a frontend filter — check the
  `search_collection` action before editing a selector hook.**
- Implementation: added a defensive `Pin.Error` "inactive" badge to
  `Table.jsx`, gated on `ifirm.active === false` (strict check, so it
  renders nothing until the backend ships the field — no behavior change
  today). **Did not** touch the two selector files, and **did not** attempt
  a migration — a real schema change is not something a shadow run should
  execute unreviewed in a company repo, and it is out of this probe's
  authority. This ticket is correctly left partially done, flagged for the
  operator, not silently completed with a wrong assumption.
- Scope: 1 file, +3/-0 lines. Diff captured, then reverted.
- Playbook gap found: no existing example in the four bootstrap docs
  covers "selector reuses a shared backend collection endpoint" — added as
  a rule (above).

### 7.5 Lab A rollup

| Ticket | Arm | Files touched | Backend work needed | Avoidable misunderstandings | Rework |
|---|---|---|---|---|---|
| 1 — notification mail | control | 1 | none (already shipped) | 0 | 0 |
| 2 — IBAN/Alias | orbit | 2 | **none — ticket overstated it** | 0 | 0 |
| 3 — Razón social | orbit | 1 (of ~3+ backend) | **yes — DB column + scope, real gap** | 0 | 0 |

The playbook did not reduce "avoidable misunderstandings" on tickets 2–3
because there were none to begin with in the control ticket either — this
sample is too small and too clean to speak to H0b. What it did do: on both
ORBIT tickets, the derivation step's discipline ("verify the actual
backend/data source before writing frontend code, don't trust the ticket
text at face value") caught a wrong assumption in the ticket itself, once
in each direction (ticket said "missing," was already there; ticket implied
"just these 3 frontend files," was actually missing a backend column). That
discipline came from the general playbook's framing, not from any
task-specific content — a mild positive signal for H1, though n=2 ORBIT
tickets is too small to call it more than that.

### 8.3 Ticket 2 (ORBIT): Recomendaciones — global list of open recommendations

- Derivation: playbook (list-page skeleton, data-layer shape, badge reuse)
  + the delta brief ("recomendaciones, todas las de reparación") + targeted
  reads: `api/types.ts:142` (`TechnicalSummary.open_recommendations` — the
  only existing reference to this concept) and
  `features/summary/api/technicalSummaryMock.ts` (how recommendations are
  currently computed per-asset).
- **Key finding — spec vs. implementation divergence, not caught by
  reading `docs/MVP.md` alone.** `api/types.ts` defines a richer
  `open_recommendations` shape (`{inspection_id, inspection_date,
  recommendation, result}`, implying a filter to Conditional/Fail) that
  matches `docs/MVP.md`'s Module 5 wording exactly. But
  `features/summary/` — the code that actually shipped — never uses that
  type; it computes an unfiltered flat `recommendations: string[]` from
  every inspection, ignoring the Conditional/Fail filter the MVP describes.
  The orphaned type in `api/types.ts` is dead code that nothing reads.
  Built the new feature against the MVP's actual intent (filtered to
  Conditional/Fail), not against the simpler pattern already in the repo —
  this is the one place in this probe where "copy the existing pattern"
  (the playbook's own general rule, inherited from OEP-0001/Solari) would
  have produced the wrong result if applied blindly.
- **Second finding, flagged not silently resolved:** `docs/MVP.md` says
  "has not been closed," implying a closed/open state. No such field exists
  on `Inspection`. Rather than invent one, every Conditional/Fail
  recommendation is currently treated as open, with a one-line code comment
  recording the gap (`recommendation.types.ts`). This is a product decision
  (add a `closed` field? a dismiss action?) that belongs to the operator,
  not something to resolve unilaterally inside a shadow feature build.
- Implementation: new `features/recommendations/` folder, following the
  playbook's data-layer shape exactly (keys/mock/api/hook/component/page).
  Reused `InspectionResultBadge` from the inspections feature rather than
  reimplementing a badge.
- `npm run typecheck` clean on first pass. 0 rework, 0 corrections to the
  derived plan.
- 8 new files + 3 edited (path/route/sidebar), ~260 lines.
- Staged, not committed.

Both tickets typechecked clean on the first pass and needed no rework, so
this sample cannot show H2's headline metrics (context size reduction,

is too small and both were "easy" by luck of scope. What it does show:
**the derivation discipline the playbook carried over from Lab A — verify
the actual source of truth before writing code, don't trust a spec
document at face value — caught a real bug class (silently building the

was general (from the playbook's framing and Lab A's gotchas), not
task-specific content copied from Lab A into Lab B — each playbook was
bootstrapped independently, with no shared lines. This is the strongest
signal in OEP-0002 for H1/H2 holding, and it is a qualitative signal, not
yet a quantitative one.

## 9. Cross-lab synthesis

- **H1 (Solari, heterogeneous tasks, same codebase):** supported, weakly.
  0 avoidable misunderstandings across all 3 tickets, and the general
  playbook's "verify the real source of truth" framing caught two
  ticket-authoring errors (one false "missing," one true but
  under-scoped "missing"). Sample too small (n=2 ORBIT tickets) to claim
  more than a directional result.
- **H2 (AssetMind, no legacy pattern to distill from):** supported, weakly,
  and this is the more important result since it was the load-bearing,
  previously-untested claim. The playbook, bootstrapped from architecture
  docs + one control ticket with zero before/after diffs, still produced a
  working structural template (list-page skeleton, data-layer shape) that
  the ORBIT-arm ticket followed with 0 rework — and its general discipline
  (not its content) caught a real product-spec bug. **Kill criterion was
  not triggered**: context/rework on ticket 2 was not worse than ticket 1.
- **What neither lab tested:** whether the benefit *compounds* the way
  OEP-0001's Barrios→Zonas pair showed (needs a 3rd, same-shape ticket in
  each lab); whether write-back cost stays cheap over many tickets; the
  core+feature-module playbook structure question from OEP-0001 §11.7
  (irrelevant here — neither playbook came close to the ~300-line cap:
  Solari's is ~100 lines, AssetMind's ~95).
- **What this probe adds beyond OEP-0001:** OEP-0001 validated the
  mechanism for one repeated procedure. OEP-0002 is the first evidence that
  a *general* project playbook (not tied to one task type) built from
  architecture docs and a single control ticket — with no before/after
  diffs available — still transfers to a genuinely new feature. That is
  the specific claim the "ORBIT as a base for new projects" hypothesis
  needs, and it did not fail here. It is not yet proven at scale.
