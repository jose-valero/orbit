# OEP-0001 — Feasibility Probe: Playbook for a Recurring Task Class

**Status:** Draft — run in progress
**Type:** Experimental
**Version:** 0.3.0
**Date:** 2026-09-09
**Depends on:** OEP-0000

---

## 1. Purpose

This OEP is **not** a conceptual proposal and does not classify any concept.

It is an empirical probe of the single load-bearing assumption underneath
every version of ORBIT discussed so far. It must run, and produce numbers,
before any further conceptual design work is justified.

The rule this OEP enforces: **do not build a conceptual edifice on top of
an untested assumption.**

---

## 2. The Assumption Under Test

The concrete pain: for a **recurring class of task**, the operator rewrites
the "how to do this" context from scratch every time a new ticket of that
class arrives.

> **H0 — The reusable part of a recurring task ("how this class of upgrade
> is done") can be captured once in a small, maintained playbook, so that
> each new ticket costs measurably less (human minutes writing context +
> tokens + USD + rework) than doing it from scratch, net of the playbook's
> upkeep.**

Sub-claims, each independently observable:

- **H0a** — Context derived from the playbook is *smaller* and *more
  precise* than context assembled ad-hoc for the same ticket.
- **H0b** — Fewer avoidable misunderstandings and less rework per ticket.
- **H0c** — The benefit *compounds*: ticket N is cheaper than ticket N-1
  because of what earlier tickets wrote back.
- **H0d** — The cost of write-back + keeping the playbook in sync does
  **not** exceed the savings.
- **H0e** — A small, per-ticket-derived, maintained playbook outperforms
  the project's existing large static `/docs` for the same task class.

If H0d fails, ORBIT collapses into "keep good notes". If H0e fails, ORBIT
is not distinguishable from having documentation.

---

## 3. Why This Must Be Tested First

- The same bet has been **lost** repeatedly by living documentation,
  model-driven development, and architecture decision records at scale. The
  common failure point is H0d (maintenance cost).
- `solari_cloud` has **already run** a version of this: many `.md` files in
  `/docs`, including standard patterns for view migration, forms, modals.
  The operator reports they are imprecise and inefficient in practice. This
  probe asks *why* that happens and whether "small + derived per task +
  maintained" behaves differently from "large + static".
- The competitive scan (OEP-0000 discussion) shows most of ORBIT's early
  ideas are already consensus. ORBIT's distinct value, if any, depends on
  H0 holding in a form others have not achieved.
- No collaboration episode has been observed. This OEP replaces
  introspection with one measured run.
- One structural reason to expect a different outcome than 2015-era
  attempts: the write-back can be done by the agent, not hand-written by a
  human. Whether that changes the economics is exactly what H0d measures.

---

## 4. Scope

**In scope:** one recurring task class in one repository, one agent
(Claude Code), a single hand-run loop, a fixed measurement protocol.

**Task class:** upgrade a React view from the old components / old
methodology to the new components / new methodology currently in use in
`solari_cloud`. (Tickets in the tracker are one-liners, e.g.
`[FRONTEND] Migrar vista de zonas`; the operator writes the real brief.)

**Explicitly out of scope:** any CLI or tooling, a principles document,
multi-agent / tool-agnosticism testing, multiple task classes, multiple
projects, folder-structure standards, generalising the playbook format
beyond this experiment.

The v0 artifact is disposable. It is a probe, not a foundation.

---

## 5. The v0 Artifact

### 5.1 `VIEW-UPGRADE-PLAYBOOK.md` — the playbook

A single file, capped at ~300 lines. The cap is not cosmetic: it forces the
"minimum sufficient" discipline and makes staleness visible. Sections:

- **Objetivo / cuándo aplica**
- **Procedimiento paso a paso**
- **Mapa componente viejo → nuevo**
- **Reglas de la metodología nueva** — data fetching, formularios, modales,
  estado, i18n, estilos / tokens, routing
- **Restricciones** — visual parity yes/no, untouchable endpoints, feature
  flags, browser support
- **Gotchas** — discoveries that cost time. Grows with every ticket. Core
  of write-back.
- **Estado** — views already on the new methodology / pending

Rule: every line must be something *expensive to reconstruct* — a step, a
mapping, a methodology rule, a constraint, a gotcha. Nothing trivially
derivable by reading the code. The playbook is a **distillation**, not a
pointer to `/docs`.

### 5.2 Derivation rule

Given a ticket, the agent produces `tickets/<id>-context.md` containing
only: the operator's short ticket brief, the applicable subset of the
playbook, the source files for that view, and a "done" checklist. The
operator reviews this file before execution.

### 5.3 Write-back rule

On closing a ticket: append new gotchas and decisions, update Estado. If it
would exceed ~300 lines, cut the least-useful existing lines and note what
was cut. Time it and count its tokens.

### 5.4 Verification

The ticket's "done" checklist is written *before* execution and the result
is checked against it.

---

## 6. Experiment Design

**Subject:** the next N ≥ 4 comparable "upgrade a React view" tickets in
`solari_cloud`. Run as they naturally arrive, ideally within ~2–3 weeks.

**Control arm:** ticket 1. Worked the operator's current way — using
`/docs` as they normally would, operator writing the full context brief
from scratch. Time the brief-writing separately. Keep the transcript.

**Bootstrap the playbook (one-time)** from:
1. the relevant `/docs` patterns (view migration, forms, modals, …),
   distilled — not copied,
2. a diff of 2–3 pairs of (old-style view, already-upgraded view) that the
   operator points to, to capture what actually changes and what `/docs`
   omits or gets wrong,
3. the ticket-1 transcript.
Operator reviews and corrects. Record minutes + tokens.

**ORBIT arm:** tickets 2 … N. The operator writes only the *delta brief*
(which view, peculiarities). The playbook + derivation step supplies the
rest. Each ticket runs: derive → operator review → execute → verify →
write-back.

**Staleness check:** at the start of a ticket run ~2+ weeks after the
playbook was built — how much of it is now wrong, who noticed, did the
ticket benefit.

---

## 7. Metrics

Recorded per ticket, both arms unless noted. Metric definitions are frozen
once ticket 1 starts.

### Headline
- **Human minutes writing the per-ticket context brief.** Control: the full
  brief. ORBIT: only the delta brief. This is the operator's stated pain.

### Economic
- Tokens: input / output / total (`/cost` in Claude Code)
- Session cost in USD
- Human minutes: prep (incl. brief) + interventions + review + write-back
  (write-back: ORBIT arm only)
- Wall-clock time to "done"

### Quality
- Count of redirections caused by an **avoidable** misunderstanding
- Count of rework iterations after the first "done" claim
- Bugs / regressions found in review or later

### Accumulation (ORBIT arm only)
- How many prior-ticket gotchas applied to this ticket
- Write-back cost (minutes + tokens)
- Did the derived context need correction? Lines changed
- Size of derived context vs. the `/docs` the operator would otherwise have
  leaned on

### Upfront (one-time)
- Minutes + tokens to bootstrap `VIEW-UPGRADE-PLAYBOOK.md`

---

## 8. Success and Kill Criteria

**Success:** across the ORBIT arm, brief-writing minutes and session cost
per ticket fall in a sustained way, quality holds or improves, and by
ticket 3–4 the cumulative saving exceeds (bootstrap cost + sum of
write-back costs).

**Kill / redirect:** any of —
- write-back is skipped in practice, or costs more than it saves (H0d)
- the derived context needs as much correction as writing from scratch (H0a)
- the playbook performs no better than the existing `/docs` (H0e)
- the agent ignores the playbook (not machine-usable)
- no downward trend across the series (H0c)

A kill result is still informative: it redirects ORBIT toward "make
write-back nearly free" or "the difference is not in the artifact" rather
than ending it.

---

## 9. Threats to Validity

- **Better-brief bias** — the operator unconsciously writes a sharper brief
  in the ORBIT arm and credits the playbook. Mitigation: in the ORBIT arm
  the operator writes *less* (delta only); keep every brief in the
  transcript for audit.
- **Learning effect** — the operator gets faster at the upgrade regardless
  of ORBIT. Mitigation: check whether the ORBIT arm starts lower and falls
  *faster* than a naive learning curve predicts; note it in the writeup.
- **Ticket heterogeneity** — record a rough size estimate (S/M/L) per
  ticket and normalise cost by it.
- **Single agent, single project, single task class** — results do not
  generalise. Accepted; deferred to later OEPs.
- **Experimenter bias** — the same person builds the playbook, runs the
  tickets and scores them. Mitigation: metric definitions pre-registered
  here before ticket 1; all transcripts kept for later audit.

---

## 10. Procedure

1. Choose N ≥ 4 comparable "upgrade a React view" tickets.
2. Copy `templates/VIEW-UPGRADE-PLAYBOOK.template.md`,
   `templates/metrics.template.md` and `handoff-solari.md` into
   `solari_cloud/.orbit/` (`metrics.md`, and the template kept as
   `VIEW-UPGRADE-PLAYBOOK.md` once built).
3. **Ticket 1 (control).** Operator writes the full brief from scratch
   (timed). Work the current way. Fill the metrics block. Keep the
   transcript.
4. **Bootstrap the playbook** from `/docs` patterns + 2–3 old↔upgraded view
   diffs + the ticket-1 transcript. Operator reviews. Record minutes +
   tokens.
5. **Tickets 2 … N (ORBIT).** Operator writes the delta brief only. Derive
   `tickets/<id>-context.md` → operator review → execute → verify →
   write-back → fill the metrics block.
6. **Staleness check** ~2+ weeks after the playbook was built.
7. **Write results** into Section 11: fill the tables, state the verdict
   against Section 8, snapshot the final playbook as an appendix.

Two axes are visible:
- **Structural / recurring content** — flat-to-improving across all three.
  Simple → simple (T1→T2) shows clear compounding: context −45%, review
  −40%, rework 2→0, gaps 3→2. Simple → complex (T2→T3) the structural core
  still transferred with 0 redirections.
- **Feature-specific surface** — does *not* compound, because each feature
  (avatar, multi-tab, second form, row actions, box removal) is a
  first-time occurrence. T3's ~16 gaps and its fix round are that surface
  being crossed for the first time. The test of whether *that* compounds is
  a future Employees-like view, which the series does not contain.

### 11.3 Per-hypothesis read (3 tickets: 2 simple + 1 complex)

- **H0a** — *derived context precise & small.* Supported. 0 body corrections
  on all three; context tracks view complexity (525 → 290 → 794), not
  bloat.
- **H0b** — *fewer misunderstandings / rework.* Supported for the recurring
  part: 0 avoidable misunderstandings on all three; 0 mid-implementation
  redirections. Rework on the complex view was the feature surface, not
  misread instructions.
- **H0c** — *the benefit compounds.* Supported **for the structural core**
  (T1→T2). **Not demonstrated for feature surface** — no second complex view
  to show T3's learnings paying off.
- **H0d** — *write-back stays cheap and the artifact stays lean.* **Partly
  contradicted.** Operator review time per write-back stayed low (~1–2 min),
  but the playbook hit and passed its size cap on the complex view and began
  shedding universally-useful content to absorb new surface. A single capped
  playbook does not obviously scale to a high-surface task class. The
  staleness test is still outstanding.
- **H0e** — *playbook beats the existing `/docs`.* Supported. All three
  tickets: the repo's `decision-guide.md` / `forms.md` point at the legacy
  pattern; the playbook does not. And the playbook carried per-view
  corrections and (eventually) a real fix for a reference defect — neither
  of which static `/docs` nor "copy the reference" can do. Caveat: it took
  three recurrences for the tour fix to land, so "carries fixes" is a
  property the mechanism had to be *forced* into, not one it had for free.

### 11.4 Confounds and caveats

1. **Sample shape.** Two minimal single-field views + one large
   master-detail view. Good spread for a probe, but n = 1 on the complex
   end.
2. **Operator expertise.** The operator has done this migration before; some
   of "0 avoidable misunderstandings" is skill, not the playbook.
3. **Bootstrap cost partly unmeasured** (planning-session reading/drafting,
   no token figure).
4. **Verification is by the same operator who ran each ticket**; no
   independent check.
5. **Economic data is one proxy number** (session %), on the complex ticket
   only. Simple-ticket cost was never captured.

### 11.5 Economic side

`/cost` is not available in the operator's Claude Code VS Code extension;
the Pro plan exposes only `/usage` (session / weekly %). One real figure:
Employees consumed **≈ 45% of a 5-hour session budget** for derive +
implementation + one fix round. Simple views were visibly much cheaper
(no fix rounds, ~15 min implementations) but were not measured. **ORBIT
must not claim a quantified cost saving on this data** — the qualitative
picture (≈ 1.5 h of operator attention + ~45% session for a 2 500-line
master-detail view, vs a remembered "~half a day + hand-written context"
baseline) is favourable but thin on the complex end, with no accumulation
benefit yet on the feature surface.

### 11.6 Interim verdict (3 of 3 planned tickets; staleness pending)

**Feasible for the recurring structural core; bounded on feature surface.**

- The playbook mechanism works: it transferred to four real views
  (including the largest), and the structural benefit **compounds** on
  like-for-like views (T1→T2).
- It does **not** dissolve the cost of genuinely new feature work, and a
  high-surface task class like "migrate a React view" **outgrows a single
  ~300-line capped playbook** — on the complex view the artifact passed its
  cap and started trimming content that had applied everywhere.
- The "reference defects" finding hardened into a rule the hard way: a
  playbook must carry the **fix**, not a description of the defect, or the
  defect replicates every ticket (the tour bug took three recurrences).

Not "it failed." The central hypothesis (a maintained playbook makes a
recurring task cheaper, and the benefit compounds) holds for the part of
the task that actually recurs. The boundary is real and worth stating.

**Still outstanding:** the staleness check (~2026-09-23) — the real test of
whether keeping the playbook current stays cheap once the codebase has
moved under it.

### 11.7 What OEP-0002 should address

1. **Generalisation.** Does the mechanism work on a **second task class**
   (a full-page CRUD from scratch; a different repo; a non-frontend task),
   or was "upgrade a React view" a lucky fit?
2. **Playbook structure.** A high-surface task class needs more than one
   capped file. Test a **core + feature-modules** shape: a stable
   structural core, plus small modules (avatar upload, multi-tab form,
   password rules, non-CRUD row actions) pulled in only when the ticket
   touches them.
3. **"Carry fixes, not warnings"** as an explicit ORBIT rule — with a
   check that a documented defect actually ships its remedy, since the
   mechanism did not enforce this on its own.
4. **Independent verification** — the current run has none.
